# Code Helper 后续优化路线图

## 1. 文档目的

本文基于仓库根目录外的《Coding Agent 开发流程与项目方案》、当前 `Code-Helper` 实现、提交历史和自动化测试，回答两个问题：

1. 已经完成的能力中，哪些仍需要从“基础可用”加固到“可信可用”。
2. 在不偏离原开发流程的前提下，下一阶段最值得实现什么。

本文不是重新设计项目，也不把业界产品功能清单直接搬进来。所有建议都服从原开发流程的核心判断：

> 一个功能只有在它能提高真实编程任务完成能力，或提高自主操作可信度时，才值得占用开发时间。

## 2. 必须保持的边界

后续优化继续遵守以下约束：

- Agent Loop、状态管理、上下文构造、Tool Calling 解析、工具执行、权限、恢复和终止逻辑继续自行实现。
- 不封装 Codex、Claude Code、Cline、Aider、DeepSeek Harness 等现有 Agent 产品。
- 不引入 LangChain、LangGraph、OpenAI Agents SDK、AutoGen、CrewAI 等 Agent 框架或 SDK。
- 不用云端 Code Interpreter、Files API 或远程执行服务替代本地工具。
- 不把多 Agent、完整容器沙箱、插件市场、自动提交/推送/PR、多模型路由作为近期目标。
- 保持“只追加事件日志”“读取后修改”“统一权限管线”“修改后验证”“轻量检查点”这些已有设计，不用新功能绕过它们。
- 继续优先保证 CLI 和本地 Web 使用同一个 Agent Core。

## 5. P0：先补齐可信执行

### R1. 真正可中止的运行预算

**实施状态：V1 已完成（2026-08-28）**

- 共享 `CancellationToken` 可中断模型请求、审批等待和 Tool Task；Web 停止接口发布请求与完成事件。
- `RunBudget` 统一执行 wall-time、Step 和供应商回报 Token 预算，耗尽后以带原因的 `PARTIAL` 结束。
- shell 在 Windows 使用 `taskkill /T /F`、在 POSIX 使用独立进程组终止子进程树；超时和取消返回不同结构化代码。
- Web“智能”面板展示 Step、时间和 Token 遥测，“轨迹”面板展示停止与预算耗尽原因。
- 已有模型请求中断、Web 端到端停止、时间/Token 门禁和 Windows 子进程树清理测试。

已知边界：供应商仅在响应结束后返回 usage 时，Token 是请求间硬门禁，不能在单次生成的任意 Token 点精确中断。Windows 本地与 Ubuntu CI 已通过同一子进程树测试。

**当前差距**

- 当前预算是单 Turn 范围，不包含跨恢复 Session 的累计费用上限。
- 模型流的 Token 硬上限仍受供应商协议和 `max_tokens` 能力约束。
- 尚未记录停止请求到模型或进程实际退出的延迟分布。

**后续加固**

- 对支持单次输出上限的供应商下传剩余生成预算。
- 记录停止请求到模型/进程真正退出的延迟指标。

**验收标准**

- 点击停止后，模型流和测试进程在可量化时间内结束，状态稳定为 `CANCELLED`。
- 达到时间或 Token 预算时进入 `PARTIAL`，事件中明确是 `TIME_BUDGET_EXHAUSTED` 或 `TOKEN_BUDGET_EXHAUSTED`。
- Windows 和 Linux 均有子进程树取消测试，不遗留后台进程。

### R2. 事件归约器与可恢复审批

**当前差距**

- `restore_from_events` 可以恢复消息、计划和统计，但没有完整重建 `pending_approval`、最近 Action、修改序列和验证序列。
- 审批请求发生后若进程重启，无法严格恢复到“等待同一个 Tool Call”的状态。
- EventStore 遇到一行损坏 JSON 会使整个 Session 加载失败；事件没有 schema version 和稳定 event id。

**建议实现**

- 把恢复逻辑抽成唯一的 `SessionReducer.apply(event)`，在线状态推进和离线恢复共享同一套归约规则。
- 为事件增加 `schema_version`、`event_id`、`causation_id`，Tool Call 使用稳定 id 做幂等判断。
- 从 `approval_requested` 与 `approval_result` 重建待审批状态；发现 `tool_started` 但没有 `tool_result` 时标记为 `INTERRUPTED_UNKNOWN`，绝不自动重放写操作。
- 恢复修改和验证序列，保证重启后 `verification_is_fresh` 不会被错误重置。
- 对尾部半写事件做容错：保留此前有效事件，隔离损坏行并发布恢复诊断；中间损坏则拒绝静默恢复。

**验收标准**

- 在“等待审批、文件刚写完、命令运行中、验证刚完成”四个位置模拟崩溃，恢复后都不会重复执行副作用。
- 同一 Tool Call id 最多产生一个成功副作用结果。
- 恢复后的最终报告与崩溃前的事件事实一致。

### R3. 验证证据加固

**实施状态：V1 已完成（2026-08-29）**

- `VerificationEvidence` 记录命令、类型、来源、起止事件、退出码、关联文件、输出摘要、适用性与拒绝原因。
- 仅可识别的测试、构建、Lint、类型检查、编译命令，或用户原文明确指定的实质性自定义命令可以满足完成契约。
- `echo`、`pwd`、未知命令和可能用 `|| true` 掩盖失败的命令不会刷新验证新鲜度。
- 定向单测会保守拒绝无法证明覆盖全部修改文件的多文件任务；证据可跨 Session 事件恢复，并在 Web“智能”面板展示。

后续加固方向是利用依赖图和项目配置提高“相关测试”范围判定精度；在此之前宁可返回 `PARTIAL`，不推测无证据的覆盖关系。

**当前差距**

- 尚未利用导入图或覆盖率数据证明目标测试与修改文件的真实依赖关系。
- 用户自定义命令目前要求完整命令文本出现在本轮任务原文中，尚未提供独立的项目验证配置文件。

**建议实现**

- 引入 `VerificationEvidence`，至少记录命令、类型、来源、开始/结束事件序列、退出码、关联修改文件和输出摘要。
- 验证来源分为：用户明确指定、项目配置推断、相关测试推断、人工核验；只有前三类成功证据可以自动满足完成契约。
- 建立轻量验证命令识别器，识别 pytest、unittest、npm/pnpm test、构建、lint、typecheck 等；未知命令即使成功，也只算普通命令。
- 按修改文件关联验证范围。跨文件修改不能只凭无关的单个测试自动宣布完全完成。
- 最终报告展示“为何该证据适用”，而不只展示退出码。

**验收标准**

- `echo ok`、`pwd` 等命令不能被标记为自动化验证。
- 用户明确指定的自定义验证命令仍可被接受，并标记来源为 `user_requested`。
- 写入发生后，所有旧证据立即失效；恢复 Session 后仍保持相同结论。

### R4. 权限能力与审批策略分离

**当前差距**

- 权限判断主要依据工具风险枚举；所有命令都询问，用户容易产生审批疲劳。
- 破坏性命令依赖少量正则黑名单，换一种 shell 写法就可能绕过。
- 当前没有独立表达网络、工作区外路径、内部运行目录、安装依赖和长时命令等能力。

**业界借鉴**

OpenAI Codex 将 Sandbox Mode（技术上能做什么）和 Approval Policy（何时询问用户）分开，并默认关闭命令网络、限制工作区写入。这里应借鉴“能力边界与审批时机分离”，但不需要近期实现完整容器沙箱。

**建议实现**

- 将工具请求归一化为能力集合，例如 `workspace.read`、`workspace.write`、`process.exec`、`network.egress`、`path.outside_workspace`、`dependency.install`、`destructive.restore`。
- PermissionPolicy 根据模式、能力、命令分类和会话授权返回 `allow / ask / deny`。
- 为命令工具增加优先使用 `argv` 的结构化入口，保留 shell 字符串作为兼容路径并提高风险等级。
- 自动允许确定性的只读检查命令；修改、网络、安装、长时间和破坏性操作继续询问。
- 支持范围明确的“本会话允许同类操作”，授权必须包含工具、路径/命令前缀、过期时间，不能保存宽泛永久权限。
- 将 `.git`、`.code-helper` 内部状态、凭据路径和工作区外路径作为独立保护规则。

**验收标准**

- 等价的危险命令不能仅通过大小写、引号、PowerShell 别名或命令拼接绕过策略。
- Plan/Ask 模式在 Tool Schema 暴露和执行层都拒绝写能力。
- 会话授权只匹配被批准的精确范围，新会话不会继承。

### R5. 冲突安全的检查点恢复

**实施状态：V1 已完成（2026-08-29）**

- Manifest 同时保存修改前基线和每次 Agent 修改后的最新副本、哈希、工具及事件序列。
- 恢复前对全部选中文件执行原子预检；任一文件与 Agent 最后产物不一致时，普通恢复零写入并返回 `RESTORE_CONFLICT`。
- 冲突响应包含外部修改 Diff 与预计恢复 Diff；Web 要求第二次明确确认后才允许强制覆盖，确认绑定当前文件哈希，内容再次变化后旧确认自动失效。
- 支持按文件选择恢复；恢复事件记录文件、预览与是否强制，并使旧验证失效。

后续可把文件选择和 Diff 预览做成专用恢复对话框；V1 已满足“不静默覆盖”的安全不变量。

**当前差距**

- 当前 Web 使用浏览器确认框完成二次确认，尚未提供逐文件勾选的可视化恢复对话框。
- 文本 Diff 限制为 1 MB；二进制或超大文件只返回哈希冲突信息。

**业界借鉴**

Cline 提供按时间点比较和恢复文件/任务的体验。本项目应只借鉴“可比较、可选择、可追踪”的交互，不照搬 shadow Git，也不改写真实 Git 历史。

**建议实现**

- Manifest 同时记录修改前哈希、Agent 修改后哈希、事件序列、触发工具和计划快照。
- 恢复前比较当前哈希与最近 Agent 产物哈希；若不一致，返回 `RESTORE_CONFLICT` 并展示 Diff，要求用户再次明确确认。
- 支持预览恢复内容和按文件选择恢复；首版仍保留每 Turn 一份轻量基线。
- 恢复本身作为一次 Mutation，旧验证立即失效，并发布完整恢复事件。

**验收标准**

- Agent 修改后用户再编辑同一文件时，普通恢复不会静默覆盖用户内容。
- 恢复新建文件、删除文件和多文件修改均可重复测试。
- 恢复后的 Diff、验证状态和事件日志一致。

### R6. 可重复 Eval 基准与质量门禁

**实施状态：V1 已完成（2026-08-29）**

- `evals/tasks/` 提供 10 个版本化 JSON 契约，覆盖项目问答、单文件缺陷、跨文件功能、并发修改、拒绝审批、检查点恢复、卡死终止、长输出取消、Session 中断和敏感环境。
- 确定性 `ScriptedModel` 复用真实 Runtime、AgentLoop、权限、工具和事件管线，一条命令生成 JSON/Markdown 报告。
- 首份基线为：契约通过率、可完成任务完成率、安全拦截率、修改后新鲜验证率、Recall@5 与首次相关文件命中率均为 100%；平均 3.4 Steps、2.6 次工具调用，脚本化 Token 共 952。
- CI 在 Python 3.11 上比较 `evals/reports/baseline.json`，任一核心比率回退、基线任务缺失或质量门禁失败都会阻断，并上传当次报告。
- 真实模型模式必须显式传入 `--allow-paid`，记录供应商、模型、推理档位、Prompt 哈希、代码提交和可选费用估算，但不作为唯一 CI 门禁。

**当前边界**

- 确定性结果验证的是 Agent 契约和执行管线，不代表真实模型智能水平。
- 真实模型首版只启用项目问答、单文件缺陷和跨文件功能三类任务，其余安全场景仍由确定性层控制变量。
- `sensitive_environment` 当前只证明命令环境不会继承 API Key；用户消息、工具输出和事件落盘的统一脱敏仍属于 R7。
- Session 中断任务证明副作用不会被自动重放；等待同一审批的完整恢复仍属于 R2。

**建议实现**

- 新建 `evals/`，每个任务包含初始仓库 fixture、用户任务、允许能力、期望文件状态、验证命令和安全断言。
- 至少覆盖项目问答、单文件缺陷、跨文件功能、并发修改、拒绝审批、回滚、卡死、长输出、Session 恢复和敏感信息十类场景。
- 提供确定性的 ScriptedModel 回归和可选真实模型评测；CI 默认只跑确定性版本，真实模型需要显式 Key 和预算。
- 生成 JSON 与 Markdown 报告，记录完成率、安全拦截率、修改后验证率、平均 Step、Token、耗时和失败分类。
- 每个优化 PR 必须对比基线，不能只报告“测试通过”。

**验收标准**

- 基准任务可一条命令重复运行，失败能定位到具体任务和契约。
- 安全用例拦截率为 100%，有验证条件的修改任务验证率为 100%。
- 真实模型结果保存模型名、配置和随机性条件，避免不可比较数据。

### R7. 日志完整性与敏感信息脱敏

**当前差距**

命令环境会移除名称含 Key/Token/Secret 等标记的变量，但用户消息、Tool 参数、stdout/stderr、模型错误和事件 payload 仍可能包含凭据。只追加日志提高了审计能力，也扩大了敏感信息落盘面。

**建议实现**

- 在 EventStore 写入前增加统一 `Redactor`，处理常见 API Key、Authorization header、URL 凭据和配置字段；保留原始数据的功能必须显式关闭且默认不可用。
- 为每行事件增加内容校验和；Session 报告显示事件缺口、损坏和恢复警告。
- 工具完整输出引用同样经过脱敏，并设置单 Session/目录磁盘配额和清理策略。
- 增加仓库内凭据扫描测试和运行时日志脱敏测试。

**验收标准**

- 将模拟 Key 放入用户消息、命令参数、stderr 和模型错误，所有持久化文件中都只能看到掩码。
- 日志篡改或中间缺行可被检测，不能以“完整轨迹”展示。

## 6. P1：提高仓库理解和工作流质量

### R8. 路径相关的 `AGENTS.md` 规则链

**当前差距**

`ContextManager` 当前递归读取多个 `AGENTS.md` 并统一注入，可能把与当前任务文件无关的子目录规则放入上下文，也没有 `AGENTS.override.md` 和明确的覆盖顺序。

**业界借鉴**

OpenAI Codex 的公开规则是从项目根目录沿当前工作目录向下构造指令链，每层只选一个规则文件，越靠近目标目录优先级越高，并设置总字节上限。

**建议实现**

- 根据当前任务候选文件或工作目录构造 `root -> target directory` 规则链。
- 每层优先 `AGENTS.override.md`，否则读取 `AGENTS.md`；同层不同时加载两份。
- 记录每条规则的来源、作用域和截断状态，Web UI 可展示本 Step 实际生效的规则。
- 多个目标目录存在冲突时显式标注，不让模型猜测覆盖关系。

### R9. Repo Map 依赖图与预算化注入

**当前差距**

Repo Map Lite 已能提取 Python 顶层符号并按文件名关键词排序，但还没有利用导入关系做图排名，也没有按实际 Token 预算自动注入每次模型请求。

**业界借鉴**

Aider 的 Repo Map 使用文件依赖图、关键符号和动态 Token 预算选择最相关部分。本项目只需实现轻量版本，不需要复制完整算法。

**建议实现**

- 解析 Python 导入边和测试到实现的关联，计算简化 PageRank/引用次数。
- 综合任务关键词、导入中心性、最近工具涉及、修改文件和测试关联评分。
- Repo Map 使用独立字符/Token 预算；没有已读文件时适当扩大，已有明确目标后收缩。
- 以文件哈希做增量缓存，只重建发生变化的节点。
- 在 `context_built` 事件记录候选数、选中原因、预算和被截断部分。

### R10. 高保真上下文压缩

**当前差距**

当前历史摘要主要是早期消息的字符摘录。Turn 结束后的结构化总结和长期记忆已经存在，但尚未统一用于 Step 级上下文压缩。

**建议实现**

- 压缩输入以事件为事实源，而不是直接摘要模型自述。
- 结构固定为目标、约束、已读文件及哈希、已改文件、工具证据、计划、失败尝试、审批决定、验证和下一步。
- 保留摘要版本和覆盖的事件序列范围；新摘要只替换已确认覆盖的旧摘要。
- 优先使用供应商 Token usage 或 tokenizer，字符预算作为降级路径。
- 摘要失败或溢出恢复失败时保留旧摘要与原事件，不改变任务结果。

### R11. 可配置但受控的生命周期 Hooks

**当前差距**

仓库已有 `HookManager` 和 Pre/Post 单元测试，但 Runtime 默认创建的是空 HookManager；开发流程建议的 `OnVerification`、`OnTaskEnd` 以及真实格式化/验证 Hook 尚未落地。

**业界借鉴**

Claude Code Hooks 使用明确事件、matcher、结构化 JSON 输入输出、超时和决策结果。可借鉴协议清晰度，但本项目首版只支持少量本地 Hook，不开放任意插件系统。

**建议实现**

- 支持 `PreToolUse`、`PostToolUse`、`OnVerification`、`OnTaskEnd` 四种事件。
- Hook 配置包含 matcher、命令 argv、超时、允许的工作目录和失败策略。
- Hook 返回结构化 `allow / deny / additional_context`；Hook 不能绕过 PermissionPolicy。
- 默认只注册安全的内部 Hook，例如 Python 修改后的可选格式检查和结束前验证缺口检查。
- Hook 自身命令也经过工作区、环境脱敏、超时和审批策略。

### R12. 命令增量输出与统一运行可观测性

**当前差距**

shell 当前等待 `communicate()` 完成后才返回 stdout/stderr。长测试期间 Web UI 不能持续展示进度，也不利于快速取消和判断卡死。

**建议实现**

- 并发读取 stdout/stderr，发布带顺序号的 `tool_output_delta`，最终 `tool_result` 仍提供归一化摘要。
- 限制 UI 推送速率和内存缓冲，完整输出继续写入引用文件。
- 统一记录模型等待、审批等待、工具运行、Hook、上下文构造和恢复耗时。
- WebSocket 重连通过事件 sequence 补发缺口，不重复渲染已见事件。

## 7. P2：收益明确后再做

### R13. 安全只读工具并行

只并行满足以下条件的调用：ToolRisk 为 READ、参数路径互不依赖、没有 Hook 声明串行要求、结果顺序可按原 Tool Call index 重排。写操作、命令、记忆写入和审批操作继续严格顺序执行。先用 Eval 证明仓库探索延迟显著下降，再默认启用。

### R14. 多语言符号提取与增量缓存

在 Python AST 稳定后，可按真实演示仓库需要增加 JavaScript/TypeScript、Java 或 Go 的轻量符号提取。优先使用语言自带解析器或小型语法库，不为“支持语言数量”引入大型 IDE 索引系统。每增加一种语言，都要提供符号准确率和上下文预算测试。

## 8. 明确不建议近期实施

- 多 Agent 分工、Agent Team 或自动委派。
- 完整 Docker/远程沙箱平台；近期只加固本地权限和进程边界。
- Cline 式 shadow Git；继续使用轻量文件检查点。
- 任意第三方 Hook/插件下载和插件市场。
- IDE 级语言服务器、复杂多窗口编辑器和账号系统。
- 自动提交、推送、创建 PR 或修改远端仓库。
- 复杂多模型路由、自动切换供应商和为模型数量而增加配置。
- 在没有 Eval 数据前重写 Agent Loop 或更换前端技术栈。

这些内容要么被原开发流程明确排除，要么会显著扩大攻击面和工程范围，却不能直接提高当前演示闭环的可信度。

## 9. 推荐实施顺序

### 迭代 1：停止与恢复必须可信

完成 R1、R2、R5。演示“运行中取消”“等待审批后重启”“外部修改后拒绝覆盖式回滚”。这是当前最明显的可靠性提升。

### 迭代 2：完成结论必须可信

完成 R3、R4、R7。演示伪验证被拒绝、范围化会话授权、敏感信息不会写入事件日志。

### 迭代 3：用数据驱动继续开发

完成 R6，建立 8～10 个任务基线。之后任何 Repo Map、上下文、Prompt、记忆或模型配置改动都必须提供 Eval 对比。

### 迭代 4：提升任务成功率和体验

按 Eval 结果选择 R8～R12，不要求一次全部完成。只有当探索耗时成为明确瓶颈时，再实现 R13；只有真实目标仓库需要时，再实现 R14。

## 10. 下一阶段完成定义

下一阶段不是以“又增加多少功能”验收，而以以下事实验收：

- [ ] 用户停止后没有模型流、Hook 或子进程继续运行。
- [ ] 任意关键点重启不会重复写文件或执行命令。
- [x] 未知成功命令不能冒充测试、构建或静态检查证据。
- [ ] 权限决策同时考虑能力边界和审批策略，安全用例拦截率为 100%。
- [ ] 检查点恢复不会静默覆盖 Agent 之后的外部修改。
- [ ] Session 日志中的模拟凭据全部脱敏，事件损坏可诊断。
- [x] 8～10 个 Eval 任务可重复执行，完成率和失败原因可对比。
- [x] 有自动验证条件的修改任务，修改后验证率为 100%。
- [ ] CLI、Web 和可选桌面入口仍使用同一 Agent Core 和事件事实源。
- [ ] 全量单元、集成、安全测试通过，演示任务在提交环境重新运行并留存证据。
