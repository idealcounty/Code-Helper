# Code Helper 可观测能力易用化方案

> 文档状态：后续优化指导方案  
> 适用模块：运行回放、上下文编译、记忆治理  
> 核心原则：保留底层专业能力，默认用普通用户能够理解的方式表达，技术细节按需展开。

## 1. 背景

Code Helper 已经能够记录 Agent 的运行事件、上下文来源、Token 预算、历史摘要、记忆候选、召回原因和执行证据。这些信息有利于调试和研究，但当前页面直接暴露了大量 Agent 工程术语，例如：

- Step、Event Sequence、Tool Call。
- Context Compiler、Repo Map、Token Budget。
- Recall、Candidate Memory、Conflict、Weight。
- Cache、Hook、Pipeline 和 Verification Evidence。

对于不了解 Agent 工作原理的用户，这些信息很难转化成实际判断。用户真正想知道的是：

1. Agent 刚才做了什么？
2. Agent 为什么读取这些内容？
3. Agent 记住了什么？
4. 任务是否成功，失败后应该怎么办？

因此，本次优化不删除原有可观测能力，而是在底层数据与前端之间增加一层面向用户的语义解释和信息分级。

## 1.1 当前实施状态

本轮已完成第一版落地：

- [x] 增加统一展示适配接口：`/api/sessions/{session_id}/observability/{view}`。
- [x] 回放、上下文、记忆接口保留原始数据，并额外返回面向用户的 `presentation` 视图模型。
- [x] 研究工作台默认名称改为“做了什么 / 参考了什么 / 记住了什么”。
- [x] 默认使用简单模式，提供“专业详情”开关；开关状态保存在浏览器本地，切换时复用已加载数据。
- [x] 为步骤、资料来源、记忆候选增加人类可读的状态、原因和下一步操作。
- [x] 保留原有检查、分支、比较、上下文开关、记忆确认/归档/验证等操作。

后续仍可按验收项补充更细的聚合规则、浏览器自动化测试和更多状态文案。

## 2. 优化目标

### 2.1 用户体验目标

- 第一次使用 Agent 的用户能够在 30 秒内理解三个页面的用途。
- 默认页面不要求用户理解 Step、Token、Tool Call 等术语。
- 每个页面优先回答一个明确问题，而不是罗列运行数据。
- 失败信息能够说明“发生了什么、影响是什么、下一步做什么”。
- 专业用户仍然可以查看完整事件、上下文预算和记忆评分。

### 2.2 产品目标

- 将三个分散的技术模块统一包装为“Agent 工作记录”。
- 提供“简单模式 / 专业模式”切换。
- 使用渐进式披露，默认展示结论，按需展开证据。
- 尽量复用已有 API、事件日志和记忆存储，不重写核心 Agent。
- 形成统一的状态颜色、术语、说明文字和交互动作。

### 2.3 非目标

- 不删除原始事件日志。
- 不降低现有可追踪性和审计能力。
- 不向普通用户展示模型私有思维链。
- 不使用模型生成未经验证的执行事实。
- 不改变 Agent Loop、上下文构建和长期记忆的底层语义。

## 3. 信息架构调整

### 3.1 统一入口

将当前三个模块统一放入：

```text
Agent 工作记录
├─ 做了什么
├─ 参考了什么
└─ 记住了什么
```

内部仍可保留原有模块名称，但默认界面使用用户语言。

### 3.2 名称映射

| 当前名称 | 默认名称 | 页面回答的问题 | 专业模式名称 |
| --- | --- | --- | --- |
| 运行回放 | 做了什么 | Agent 如何完成本次任务？ | 运行回放 |
| 上下文编译 | 参考了什么 | Agent 回答时使用了哪些信息？ | 上下文编译 |
| 记忆治理 | 记住了什么 | Agent 保存了哪些长期信息？ | 记忆治理 |

### 3.3 页面顶层结构

每个页面统一采用四层信息：

1. **一句话结论**：本轮发生了什么。
2. **关键事实**：重要步骤、资料或记忆。
3. **用户操作**：重试、查看文件、保存、忽略等。
4. **技术详情**：原始事件、Token、评分和哈希等。

## 4. 简单模式与专业模式

### 4.1 简单模式

简单模式为默认模式，主要展示：

- 人类可读的标题和说明。
- 三到七个关键步骤。
- 成功、进行中、等待确认或失败状态。
- Agent 使用某项信息的原因。
- 用户可以执行的下一步动作。

简单模式不默认展示：

- Event Sequence。
- 完整 Tool Arguments。
- Token 精确分项。
- 上下文哈希和缓存键。
- 记忆向量相似度。
- Hook 和 Pipeline 内部状态。

### 4.2 专业模式

专业模式保留当前能力，并增加清晰的术语解释。它可以显示：

- 每个 Step 的完整事件。
- Tool Calls 和工具返回。
- 上下文来源与 Token 估算。
- 历史摘要覆盖范围。
- 记忆召回评分、冲突和生命周期。
- 缓存、Hook、耗时和执行证据。

### 4.3 模式切换原则

- 切换模式不重新请求后端，不改变任务状态。
- 用户选择保存在本地设置中。
- 专业模式只改变展示，不扩大权限。
- 简单模式中的每个结论都应能追溯到专业模式中的实际数据。

## 5. “做了什么”页面设计

### 5.1 默认摘要

页面顶部首先给出任务结果：

```text
Agent 已完成本次修改
修改了 2 个文件，并成功通过 12 项测试。
```

失败时显示：

```text
任务停在“运行测试”阶段
原因：solution.cpp 编译失败。
建议：查看第 37 行的类型错误，然后重新运行。
```

### 5.2 故事化时间线

将底层事件聚合为用户可以理解的阶段：

```text
理解任务 → 阅读代码 → 制定方案 → 修改文件 → 运行验证 → 完成
```

同类事件应合并。例如连续读取 8 个文件，不显示 8 条 Tool Call，而显示：

```text
阅读了 8 个相关文件
重点查看：solution.cpp、README.md、tests/test_solution.py
```

### 5.3 状态映射

| 底层事件 | 简单模式表达 |
| --- | --- |
| `context_built` | 已准备本轮参考资料 |
| `tool_started: read_file` | 正在阅读文件 |
| `tool_started: apply_patch` | 正在修改代码 |
| `tool_started: run_command` | 正在运行验证 |
| `approval_requested` | 等待你的批准 |
| `verification_recorded` | 已记录验证结果 |
| `run_failed` | 任务执行失败 |
| `turn_finished` | 本轮任务结束 |

### 5.4 关键操作

根据当前状态提供明确动作：

- 查看修改文件。
- 查看失败位置。
- 重新运行验证。
- 从失败步骤重试。
- 查看完整技术记录。

不应只提供“查看详情”，而应优先提供能够解决问题的动作。

## 6. “参考了什么”页面设计

### 6.1 默认摘要

页面回答两个问题：

1. Agent 使用了哪些资料？
2. 为什么使用这些资料？

示例：

```text
本轮主要参考了 5 项内容

solution.cpp
用于理解当前算法实现。

README.md
用于确认项目的编译和运行方式。

最近对话
用于继续上一轮未完成的修改。
```

### 6.2 来源分类

将专业来源转换为用户语言：

| 底层来源 | 默认名称 | 解释 |
| --- | --- | --- |
| Repo Map | 项目结构 | 帮助 Agent 快速定位相关文件 |
| Recent History | 最近对话 | 保持当前任务连续性 |
| History Summary | 较早对话摘要 | 保留被压缩对话中的关键结论 |
| Project Memory | 项目记忆 | 使用已确认的项目事实和决策 |
| User Memory | 使用习惯 | 使用用户允许保存的长期偏好 |
| Tool Result | 执行结果 | 使用读取、搜索或测试的实际结果 |
| Skill | 工作方法 | 使用特定任务的操作流程 |

### 6.3 上下文预算简化

默认使用状态语言代替精确 Token 数：

- **充足**：还有足够空间，可继续工作。
- **较多**：资料较多，但当前仍可正常处理。
- **已整理**：旧内容已自动摘要。
- **接近上限**：部分低优先级内容可能被省略。

专业模式再展示：

```text
85,000 / 80,000 chars
24,000 estimated tokens
23 次压缩
```

### 6.4 “为什么选择”解释

每个来源至少提供一条确定性解释：

- 与用户问题中的文件名匹配。
- 包含相关函数或类。
- 被当前文件导入。
- 最近被 Agent 修改。
- 来自用户确认的长期记忆。

解释应来自可验证规则，不应虚构选择原因。

## 7. “记住了什么”页面设计

### 7.1 默认分类

将内部记忆类型转换为用户概念：

| 内部类型 | 默认名称 | 示例 |
| --- | --- | --- |
| fact | 项目事实 | 项目使用 C++17 |
| decision | 已做决定 | 测试框架选择 pytest |
| preference | 你的偏好 | 默认使用中文回答 |
| task | 待办事项 | 补充算法边界测试 |

### 7.2 记忆卡片

每条候选记忆显示：

```text
你偏好算法题使用 C++17

来源：你在 3 次对话中提到
用途：以后生成算法代码时优先选择 C++17
状态：等待确认

[保存] [修改] [不要记住]
```

### 7.3 候选、冲突和重复

默认不直接展示聚类分数和相似度，而是转换成建议：

```text
发现 6 条内容相近的记忆
建议合并为：“算法题默认使用 C++17”

[合并并保存] [逐条查看] [全部忽略]
```

冲突时显示：

```text
发现两条不一致的偏好

旧记录：默认使用 Python
新记录：算法题默认使用 C++17

[保留新记录] [保留旧记录] [分别保留]
```

### 7.4 召回解释

当一条记忆被当前任务使用时，显示：

```text
本轮使用了这条记忆
原因：你正在解决算法题，并且该偏好与语言选择相关。
```

专业模式可以继续展示文本匹配分、语义分和仓库证据。

## 8. 抽象适配层

### 8.1 总体结构

```text
事件日志 / 上下文快照 / 记忆存储
                ↓
        Presentation Adapter
                ↓
     面向普通用户的 View Model
                ↓
       简单模式 / 专业模式 UI
```

底层数据继续作为唯一事实来源。适配层只负责：

- 聚合同类事件。
- 映射专业术语。
- 生成可追溯的状态说明。
- 推荐用户操作。
- 控制信息层级。

### 8.2 推荐的 View Model

```json
{
  "summary": {
    "status": "completed",
    "title": "Agent 已完成本次修改",
    "description": "修改了 2 个文件，并通过 12 项测试。"
  },
  "items": [
    {
      "id": "read-code",
      "label": "阅读代码",
      "description": "查看了 5 个相关文件",
      "status": "completed",
      "evidence_sequences": [31, 32, 33]
    }
  ],
  "actions": [
    {
      "type": "open_file",
      "label": "查看修改文件",
      "target": "solution.cpp"
    }
  ],
  "technical_details_available": true
}
```

`evidence_sequences` 用于从简单描述跳转到专业模式中的原始证据。

### 8.3 适配层实现位置

建议采用后端与前端分工：

- 后端负责事件聚合、状态判断和证据关联。
- 前端负责模式切换、卡片呈现和渐进式展开。
- 原始 API 保留，新增面向展示的 `view` 或 `summary` 字段。
- 不建议只在前端硬编码全部事件解释，否则不同客户端容易产生不一致。

## 9. 文案规范

### 9.1 状态文案

| 状态 | 推荐文案 | 颜色 |
| --- | --- | --- |
| running | 正在处理 | 青蓝 |
| waiting | 等待你的操作 | 琥珀 |
| completed | 已完成 | 绿色 |
| warning | 需要注意 | 橙色 |
| failed | 未能完成 | 红色 |
| cancelled | 已停止 | 灰色 |

### 9.2 文案原则

- 先说结果，再说技术原因。
- 避免只显示错误码。
- 每个失败状态尽量提供一个可执行建议。
- 不使用“智能地”“自动理解”等无法验证的描述。
- 明确区分“事实”“估计”和“建议”。

示例：

```text
不推荐：CONTEXT_COMPACTED · 42 messages omitted

推荐：较早的 42 条消息已整理成摘要，不影响最近对话继续进行。
```

## 10. 实施阶段

### Phase 1：统一入口与术语

- 新增“Agent 工作记录”统一入口。
- 将三个标签改为“做了什么 / 参考了什么 / 记住了什么”。
- 增加简单模式与专业模式开关。
- 建立统一状态颜色和术语表。

验收：新用户不阅读帮助文档也能说出三个页面的用途。

### Phase 2：任务过程摘要

- 将事件聚合为任务阶段。
- 合并连续的读取、搜索和修改操作。
- 提取修改文件、验证结果和失败原因。
- 增加查看文件、重试和查看证据操作。

验收：普通用户能在一分钟内说明 Agent 做了什么、是否成功。

### Phase 3：参考资料解释

- 将上下文来源转换为用户语言。
- 为每个来源提供选择原因。
- 将上下文预算改为状态化表达。
- Token 和压缩细节移入专业模式。

验收：用户能够理解 Agent 为什么读取某个文件，以及内容是否被压缩。

### Phase 4：记忆卡片与治理建议

- 使用事实、决定、偏好和待办四类卡片。
- 显示记忆用途和来源。
- 将重复、冲突转换为合并或选择建议。
- 增加保存、修改、忽略、归档操作。

验收：用户不需要理解向量召回，也能正确处理候选和冲突记忆。

### Phase 5：引导与产品验收

- 增加首次进入页面的简短引导。
- 增加术语提示和空状态示例。
- 检查窄屏、键盘操作和可访问性。
- 使用真实用户任务验证理解成本。

## 11. 测试计划

### 11.1 功能测试

- 简单模式和专业模式切换。
- 页面刷新后保留模式选择。
- 运行中、等待审批、成功、失败、取消状态。
- 多次文件读取能够正确合并。
- 简单摘要能够跳转到原始证据。
- 上下文发生压缩后的状态说明。
- 候选记忆确认、拒绝、合并和冲突处理。

### 11.2 可理解性测试

邀请不了解 Agent 内部实现的用户完成以下问题：

1. Agent 是否完成了任务？
2. Agent 修改了哪些文件？
3. Agent 为什么读取 README？
4. 是否发生了上下文压缩？
5. 哪条内容将被长期记住？

目标：无需帮助即可正确回答至少 4 个问题。

### 11.3 回归测试

- 专业模式仍能查看原始事件和上下文数据。
- 简单摘要与底层事件状态一致。
- 不泄露 API Key、敏感命令参数或私有推理内容。
- 记忆操作仍需遵守现有人工确认边界。
- 展示适配层不能改变 Agent 执行结果。

## 12. 验收标准

本轮易用化完成需要满足：

- 存在统一的“Agent 工作记录”入口。
- 默认标签为“做了什么 / 参考了什么 / 记住了什么”。
- 默认简单模式不直接暴露大量内部术语。
- 专业模式能够查看现有全部技术信息。
- 每个简单结论都能追溯到原始证据。
- 失败页面同时提供原因、影响和下一步操作。
- 上下文压缩能够被普通用户理解。
- 记忆候选能够通过自然语言完成确认和治理。
- 不修改 Agent Loop、权限和持久化语义。
- 现有 Web 测试和完整 CI 通过。

## 13. 推荐优先级

如果开发时间有限，优先顺序为：

1. 统一入口和名称。
2. “做了什么”的任务摘要。
3. “参考了什么”的来源解释。
4. “记住了什么”的候选卡片。
5. 专业模式细节和首次使用引导。

其中前两项最能降低第一次使用时的理解成本；后续三项负责保留 Code Helper 在可观测性、上下文和记忆治理上的差异化优势。

## 14. 最终产品表达

优化后可以这样介绍：

> Code Helper 不只是记录 Agent 的内部事件，而是把它们转换成普通用户能够理解的工作说明。用户可以直接看到 Agent 做了什么、参考了什么、记住了什么；需要调试时，再切换到专业模式查看完整 Step、上下文预算和记忆证据。
