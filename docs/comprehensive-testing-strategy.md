## 1. 测试目标

这套测试不只回答“代码能不能运行”，还要回答以下问题：

1. Agent Loop 的状态转移、终止和异常恢复是否正确。
2. Ask、Plan、Act、任务类型、推理强度和审批策略是否真正生效。
3. 文件、命令、Git、记忆、Skills 和算法 Tools 是否安全可靠。
4. 上下文压缩、Repo Map 和跨对话记忆是否有确定性证据。
5. 多轮任务、并发会话、取消、审批和长输出下是否仍然稳定。
6. Web UI、WebSocket 和桌面 EXE 是否具备完整用户体验。
7. Agent 生成和修改代码的质量是否能通过可重复的 Eval 证明。
8. 所有结果能否关联到代码提交、测试环境和原始日志。

最终需要形成两类结论：

- **工程结论**：接口、状态机、权限和数据持久化符合预期。
- **能力结论**：在固定任务集上，Agent 的完成率、验证率、检索效果和算法可靠性达到基线。

## 2. 测试原则

- **风险优先**：优先测试可能修改文件、执行命令、泄露密钥或卡死的路径。
- **分层测试**：单元测试发现局部错误，集成测试验证模块协作，端到端测试验证用户流程。
- **确定性优先**：默认使用 Scripted/Fake Model，避免模型波动和 API 费用影响基础回归。
- **真实模型补充**：DeepSeek 测试单独执行、重复多次，并记录模型与费用，不能替代确定性测试。
- **证据优先**：每次测试都保存命令、提交哈希、环境、原始结果和汇总结论。
- **失败也保留**：失败报告、最小反例和修复前后对比属于重要面试证据，不应只保留全绿截图。
- **不伪造数据**：文档中的阈值是验收目标，只有实际执行后才能写入“实测结果”。

## 6. 单元测试方案

### 6.1 Agent Loop 与状态机

重点验证：

- 初始状态能够进入上下文构建和模型请求。
- 模型返回文本时正常结束。
- 模型返回 Tool Calls 时进入工具执行并回到下一 Step。
- Tool Call 与 Tool Result 一一配对。
- Plan 模式生成计划但不执行写操作。
- Ask 模式禁止修改类 Tools。
- Act 模式在权限允许时执行操作。
- 达到 Step、Token、耗时或重复动作预算后确定性终止。
- 用户取消后尽快进入 cancelled 状态。
- Tool、模型、验证 Hook 抛出异常时产生正确错误码。
- 重复写入和卡死恢复不会反复执行副作用。

建议关键模块行覆盖率不低于 90%，分支覆盖率不低于 80%。

### 6.2 权限系统

对三种审批策略建立参数化测试矩阵：

| 操作 | 请求批准 | 帮我批准 | 完全放开 |
| --- | --- | --- | --- |
| 只读文件 | 默认允许 | 默认允许 | 允许 |
| 写文件 | 弹出审批 | 按安全规则自动处理 | 允许 |
| 普通命令 | 弹出审批 | 按安全规则自动处理 | 允许 |
| 高风险命令 | 必须拒绝或人工确认 | 不得越过硬安全边界 | 不得越过硬安全边界 |
| 工作区外路径 | 拒绝 | 拒绝 | 拒绝 |

还需覆盖：

- 仅允许本次与本会话允许的授权范围。
- 审批 ID 缺失、过期或重复提交。
- 刷新页面后待审批状态恢复。
- 拒绝操作后 Agent 能继续或安全终止。
- 会话 A 的授权不能被会话 B 使用。

### 6.3 文件、命令与 Git Tools

- 正常路径、空文件、Unicode 文件名和长路径。
- 相对路径、绝对路径、`..` 路径穿越和符号链接边界。
- 读大文件时头尾裁剪与完整结果引用。
- Apply Patch 成功、上下文不匹配、重复 Patch 和外部并发修改。
- 命令成功、非零退出、超时、取消和超长输出。
- 命令环境不继承 API Key 等敏感变量。
- Git 状态、Diff、未初始化仓库和脏工作区。
- Checkpoint 创建、恢复、冲突和部分失败。

### 6.4 上下文与 Repo Map

- 字符预算、Token 估算和不同编码文本。
- 最近消息保留顺序正确。
- 工具协议消息不会因裁剪形成非法历史。
- 超预算时生成摘要并发布 `context_compacted` 事件。
- 文件摘要缓存命中，文件修改后正确失效。
- Repo Map 对文件名、符号、导入关系和最近修改的打分。
- Repo Map 关闭后不再注入，但其他上下文来源仍有效。
- 大仓库截断后结果稳定且可解释。

建议对预算计算、路径排序和摘要边界增加基于 Hypothesis 的性质测试。

### 6.5 记忆系统

- 候选记忆生成、确认、拒绝和批量处理。
- 未确认候选不能进入长期记忆。
- 项目记忆只在当前项目召回。
- 用户记忆关闭时不得跨项目注入。
- 重复候选合并、冲突检测和主题归类。
- 固定、归档、恢复、过期、遗忘和重新验证。
- 进程重启后长期记忆仍能恢复。
- 召回结果带有来源和评分证据。
- 记忆文件损坏时能够降级，而不是阻止应用启动。

### 6.6 Skills、Hooks 与任务类型

- Skills 目录加载和按需启用。
- 禁用 Skill 后不能被 Agent 加载。
- Pre/Post/Verification/TaskEnd Hook 的顺序和失败隔离。
- 自动任务分类器对算法题、项目开发和普通问答的识别。
- Algorithm/Profile 与 Project/Profile 的 Tool 白名单不同。
- Fast、Balanced、Deep 的配置映射正确。

### 6.7 算法实验室

- 约束解析器对整数范围、总和约束和多测试用例的识别。
- 固定种子的边界测试和随机测试可复现。
- Candidate 与 Oracle 输出一致和不一致的情况。
- 超时、编译失败、运行时错误和输出格式错误。
- Shrink 能找到更小的失败反例。
- 报告中的通过数、P95、复杂度和证据路径正确。
- 缓存只复用相同代码、命令、用例和配置的结果。
- 算法实验按钮不触发不必要的模型请求。

## 7. 组件与集成测试

### 7.1 Runtime 集成

使用临时工作区和 ScriptedModel，运行真实 Runtime、Agent Loop、权限、Tools、事件、上下文和验证管线。

核心场景：

1. 项目问答：读取相关文件后回答，不修改文件。
2. 单文件修复：检查点、写入、验证和最终证据完整。
3. 跨文件功能：Repo Map 定位文件，修改多个文件并运行测试。
4. 外部并发修改：拒绝覆盖未预期的新内容。
5. 审批拒绝：不产生写副作用。
6. 检查点恢复：文件恢复且事件可追踪。
7. 卡死终止：重复动作被阻断。
8. 长输出取消：工具进程结束且 UI 可再次交互。
9. 会话中断：不自动重放未知副作用。
10. 敏感环境：命令与日志中没有 API Key。

这些场景与仓库现有 `evals/tasks/` 保持一致，避免维护两套含义不同的任务。

### 7.2 API 契约测试

当前由 `scripts/api_contract_smoke.py` 执行 32 项确定性 HTTP/WebSocket 契约检查，并由统一质量门禁强制运行；它使用临时工作区和 ScriptedModel，不消耗真实模型额度。

覆盖所有核心路由：

- 健康检查、设置读取与保存。
- 会话创建、列表、归档、恢复和模式切换。
- 消息发送、运行状态、取消和错误响应。
- 文件浏览、文件读取和工作区边界。
- 审批提交：合法、缺字段、过期和重复请求。
- 智能面板、运行回放、上下文和记忆治理接口。
- 算法实验创建、进度、停止、报告和缓存。

每个接口至少验证：

- 正常响应状态和 JSON Schema。
- 400、404、409、422 等错误契约。
- 返回内容不包含完整 API Key、命令环境或未脱敏数据。
- 不同会话和工作区之间没有数据串扰。

### 7.3 WebSocket 集成

- 建立连接后事件 sequence 单调递增。
- 历史恢复与实时事件之间没有重复或缺口。
- 断线重连后从正确位置继续。
- 慢客户端不会无限占用后端内存。
- 一个会话断线不影响其他会话。
- 取消后最终收到 cancelled/turn_finished 事件。
- 50 个并发连接下事件仍能正确分发。

### 7.4 持久化与重启

- 创建多轮对话并保存工作区状态。
- 关闭服务后重新启动。
- 恢复会话、历史消息、计划、记忆和文件标签。
- 旧历史以最终 Markdown 直接恢复，不重新播放流式动画。
- 被中断的 Tool Call 只标记待处理，不自动执行。

## 11. 压力与性能测试

压力测试分为“不调用真实模型”和“真实模型小规模验证”两部分。大规模压力默认使用 Fake/Scripted Model，避免将供应商限流误判为本项目性能。

### 11.1 HTTP API 负载

建议使用 k6 或 Locust：

仓库也提供不依赖第三方压测平台的只读探针：

```powershell

  --url http://127.0.0.1:8765 `
  --path /api/health `
  --requests 500 `
  --concurrency 25 `
  --output-dir test-results/performance
```

| 场景 | 并发 | 时长 | 初始目标 |
| --- | ---: | ---: | --- |

阈值需要先运行基线再校准；之后将相同机器上的 P95 回退超过 20% 视为性能回归。

### 11.3 大仓库与大上下文

初始目标：

- 10MB 工具输出不能直接塞满上下文。

## 12. 故障注入与恢复测试

通过 FakeModel、临时文件和可控子进程注入故障：

- 模型连接超时、HTTP 400/401/429/500。
- 流式 Tool Call 参数被拆分或中途断开。
- Tool Result 丢失或重复。
- 文件在读取后、写入前被外部修改。
- 磁盘只读、磁盘空间不足和结果文件损坏。

- 服务在写文件后、记录结果前异常退出。

每个场景验证：

1. 是否产生稳定错误码。
2. 是否保留足够诊断证据。
3. 是否避免重复副作用。
4. 是否允许用户取消、重试或放弃。
5. 恢复后页面是否重新可交互。

## 13. 安全与隐私测试

### 13.1 密钥和敏感信息

- `.env` 不被 Git 跟踪。
- Git 当前内容和历史均扫描 API Key。
- 日志、事件、Trace、截图、测试报告不显示 Key。
- 命令 Tool 子进程不继承 Key。
- API 设置接口只返回掩码提示。
- 测试夹具只使用假密钥。

### 13.2 工作区边界

- `../`、绝对路径、URL 编码路径和大小写变体。
- Windows 驱动器切换和 UNC 路径。
- 符号链接/Junction 指向工作区外。
- 文件浏览 API 和 Tool 层都必须验证边界。

### 13.3 Web 服务

- 未配置远程访问时默认只监听 `127.0.0.1`。
- 启用共享密码后 HTTP、API 和 WebSocket 使用同一认证边界。
- 非法 JSON、超大请求体和快速重复请求不能导致服务崩溃。
- 错误响应不暴露本机敏感路径、完整环境变量或堆栈。
- Markdown 渲染和消息显示进行 XSS 测试。

### 13.4 权限不可绕过

无论 UI 选择何种审批策略，以下硬边界都必须存在：

- 不能静默写入工作区外。
- 不能泄露 API Key。
- 不能把未知中断副作用当成成功。
- 不能用简单模式或专业模式切换扩大权限。

- 保存机器环境与 Git 提交信息。

### 阶段 B：扩大确定性覆盖

- 补齐单元、性质、API 契约和 Runtime 集成测试。
- 对权限、路径、Tool 协议和取消机制重点补测。
- 建立覆盖率和变异测试基线。

### 阶段 C：用户级验收

- 自动化工作区、多轮对话、审批、停止、刷新恢复和归档。
- 覆盖普通/专业可观测界面。
- 记录浏览器截图、视频和 Trace。

### 阶段 D：性能和稳定性

- API 负载、Agent 并发、大仓库和长输出。
- 2 小时浸泡测试。
- 建立可比较的性能基线。

### 阶段 E：真实模型与发行验收

- 运行有限规模 DeepSeek Eval。
- 人工评审生成代码。
- 在干净 Windows 环境验证 EXE。
- 输出最终测试报告。

## 19. 最终测试报告模板

正式执行完毕后应生成 `docs/final-test-report.md`，至少包含：

1. 被测版本、环境和时间。
2. 各测试层的用例数、通过率和耗时。
3. 覆盖率与变异测试结果。
4. Agent Eval 完成率、安全率和验证率。
5. API/并发/浸泡测试的 P50、P95、P99、CPU 和内存。
6. E2E 和 EXE 验收结果。
7. 安全扫描结果。
8. 发现的缺陷、修复和回归证据。
9. 已知限制和未执行项目。
10. 原始证据目录与 CI 链接。

报告结论必须使用以下三种之一：

- **Passed**：全部硬门禁通过。
- **Conditional Pass**：核心功能通过，但存在已记录的低风险限制。
- **Failed**：存在 P0/P1 缺陷或核心门禁失败。

## 20. 面试展示建议

面试时不要只说“写了很多单元测试”，建议按四层证据介绍：

1. **正确性**：pytest 单元和集成测试覆盖 Agent Loop、权限、上下文、记忆和 Tools。
2. **系统可靠性**：端到端覆盖真实用户流程，故障注入验证取消、审批和中断恢复。
3. **非功能质量**：对 API、并发 Agent、大仓库和长输出进行压力与浸泡测试。
4. **Agent 特有质量**：使用确定性 Eval 和真实 DeepSeek Eval 分别证明协议可靠性与任务完成能力。

可以使用下面的简短表述：

> 我没有用一次成功演示证明 Agent 可用，而是建立了分层测试体系。底层通过单元和集成测试验证状态机、权限与工具协议；用户层通过浏览器烟测和确定性 E2E 验证界面、审批、取消和重启恢复；性能层记录并发、P95 和内存曲线；能力层使用固定任务集评估完成率、检索命中率和验证率。每次正式测试都绑定 Git Commit、环境和原始报告，因此结果可以复现，也能区分项目缺陷、模型波动和外部 API 限流。

推荐展示的证据：

- CI 全绿页面和 JUnit/覆盖率报告。
- 一张性能曲线或并发汇总表。
- 一份 Agent Eval 的 Markdown 报告。
- 一个失败反例以及修复前后结果。
- 一段完整 E2E 视频或 Playwright Trace。
- 干净 Windows 环境中的 EXE 验收记录。

## 21. 完成标准

只有满足以下条件，才能对外表述“项目经历过全面测试”：

- [x] 单元、集成、E2E、压力、安全和桌面测试均有实际运行记录；完整浏览器/WebView2 流程仍单列为人工验收项。
- [x] 自动化测试结果绑定 Git Commit、环境、时间和原始证据；人工验收仍需补充同样的记录。
- [x] 关键模块覆盖率达到已批准阈值（pytest-cov 行 86.46% / 分支 75.00%，XML/HTML 已生成）。
- [x] 关键安全不变量变异测试达到阈值（5/5 killed，Mutation Score 100.0%；使用项目内置临时副本探针）。
- [x] 确定性 Agent Eval 全部硬门禁通过（11 个固定任务，合同/完成/安全/验证率均 100%）。
- [ ] 至少完成一次真实 DeepSeek 小规模重复 Eval。
- [x] 至少完成一次并发测试和一次 2 小时浸泡测试（20 会话/5 并发完成率 100%；2 小时浸泡 45,535 会话完成率 100%）。
- [ ] 至少在一个干净 Windows 环境完成 EXE 验收。
- [ ] P0/P1 缺陷全部关闭并有回归证据。
- [x] 最终报告明确列出未执行项和已知限制。
- [x] 测试资料中不存在 API Key 或个人隐私（安全审计通过）。

在这些测试真正执行之前，推荐表述为“已建立全面测试方案并具备部分自动化基础”，而不是“已经完成全部测试”。
