# Code Helper 面试亮点与后续增强路线

## 1. 文档用途

本文是后续开发对话的接力文档。新的开发者或 Agent 阅读本文后，应能理解：

- Code Helper 当前已经具备什么能力。
- 哪些能力最适合作为面试亮点。
- 当前实现仍有哪些明显短板。
- 代码 RAG、算法编程模式和项目编程模式应该如何设计。
- 下一阶段按什么顺序实施，以及如何验收。

开始工作前还应阅读：

1. 仓库外的 `../../Coding Agent开发流程.md`，它是项目范围和优先级的主要依据。
2. `docs/architecture.md`，了解自研逻辑与第三方依赖边界。
3. `docs/memory.md`，了解当前记忆分层和已经完成的长期记忆能力。
4. `docs/optimization-roadmap.md`，了解可信执行方面的详细加固建议。

本文不能覆盖上述开发流程中的约束；发生冲突时，以开发流程和用户最新要求为准。

### 1.1 审阅结论

这条路线总体合适，但实施时必须避免把“面试上值得讲”误解为“现在都要做”。当前项目最强的叙事已经是自研 Agent Loop 与可信执行闭环；代码 RAG、TaskProfile 和算法模式只有在能够通过 Eval 证明收益时才是增强，否则会稀释主线并增加演示不稳定性。

本文采用以下修订原则：

- 先修复会导致错误完成、停止失效或覆盖用户修改的问题，再增加智能能力。
- 先建立可重复基线，再根据失败分布选择 RAG、规则链或 Profile，不凭主观感受扩展功能。
- 每次迭代只交付一个可独立验收的纵向切片；不在同一迭代同时重构 Agent Loop、权限、检索和 UI。
- 新能力默认降级可用。Embedding、FTS5、LSP 或真实模型 Eval 失败时，核心 Agent 仍能运行。
- Web UI 只展示后端已经产生的真实证据，不为尚未落地的能力制作“看起来已完成”的状态。

### 1.2 两个时间范围

路线需要区分两个时间范围，不能混在同一个冲刺中：

1. **提交稳定期**：优先处理阻塞真实任务或演示的 P0 缺陷、建立最小 Eval、复核视频和提交材料。此阶段不启动完整代码 RAG、算法模式或大型编辑器改造。
2. **面试增强期**：在提交规则允许继续开发时，再依据 Eval 结果实现代码 RAG 和 TaskProfile。若题目要求截止后不得更新公开仓库，则截止后的实验不能伪装成已提交版本能力。

## 2. 项目定位

Code Helper 不是一个大模型聊天界面，也不是现有 Agent 产品或 Agent SDK 的封装。它是一个从零实现的本地 Coding Agent：

```text
用户任务
  -> 构造上下文和计划
  -> 调用模型原生 Tool Calling
  -> 权限检查
  -> 本地读取、修改和执行
  -> 观察工具结果
  -> 验证和有限修正
  -> 输出带证据的结果
```

面试时应将项目定位为：

> 一个事件驱动、可审批、可恢复、会验证，并能逐步扩展代码级检索能力的本地 Coding Agent。

## 3. 当前已经具备的亮点

截至 2026-08-29，仓库提交版本全量自动化测试为 `160 passed`。当前最有价值的能力包括：

### 3.1 自研 Agent Core

- 自行实现异步 Agent Loop 和显式状态机。
- 自行解析模型原生 Tool Calling。
- 自行实现上下文、工具注册、参数校验、权限、终止和错误处理。
- 不依赖 LangChain、LangGraph、OpenAI Agents SDK、AutoGen、CrewAI 等 Agent 框架。

这是面试中最重要的技术基础。需要能够解释一次 Turn、Step、Action 和 Observation 如何推进。

### 3.2 可信执行闭环

- 读取文件后记录哈希，修改前验证文件没有被外部改变。
- Ask、Plan、Act 模式限制不同工具能力。
- 文件写入和命令经过统一审批管线。
- Web 顶栏支持会话级“请求批准 / 帮我批准 / 完全放开”：自动批准仍保留危险命令与工作区边界，完全放开仅在 Act 模式且经过二次确认后生效；Ask/Plan 不会因此获得更多工具。
- 修改前创建轻量文件检查点。
- 支持 Diff、回滚和验证新鲜度。
- 修改后没有新的成功验证时，不允许直接报告完成。
- 重复 Action/Observation 达到阈值时终止，避免无限循环；终止前会给模型一次有界恢复机会，提示重新观察状态或结束已完成任务。对已成功的相同写入调用先返回结构化 `DUPLICATE_TOOL_CALL` 观察，避免重复修改文件；若工具返回的文件 SHA-256 发生变化，则视为有进展，不会误判为卡死。若连续写入、无变化写入（`NO_CHANGES`）或重复写入拦截（`DUPLICATE_TOOL_CALL`）没有进展，会发布 `stuck_terminal` 并以“部分完成”结束，保留最新修改；重复读取仍按失败熔断，避免无限循环。

这一部分比增加更多模型或更多 UI 功能更有辨识度。

### 3.3 事件驱动、审计和恢复

- Session 使用只追加 JSONL 事件记录执行轨迹。
- CLI、WebSocket 和 Web UI 消费同一事件源。
- 同一 Session 已支持连续多轮对话；Web 会拒绝过期运行状态覆盖新一轮状态，发送内容立即回显，后台异常会落为可见失败事件。
- 可以恢复历史消息、计划、Token 和工具统计。
- 最终报告包含修改文件、计划、命令和验证证据。

### 3.4 上下文和记忆工程

- Repo Map Lite 提取文件类型和 Python、C++、Java、JavaScript/TypeScript、Go 的轻量顶层符号与导入信息。
- 支持项目 `AGENTS.md` 和三个按需加载的 Skills。
- 工具长输出保留头尾，完整输出单独落盘。
- 具备上下文预算、历史裁剪和摘要事件。
- 项目级长期记忆支持写入、检索、冲突、遗忘和自动召回。
- 用户级记忆默认关闭，启用后与项目记忆分目录存储。

现有 Repo Map、长期记忆和词法/Embedding 混排已经构成代码 RAG 的部分基础；Repo Map V1 已加入 Python、JavaScript/TypeScript 和 Java 静态导入中心性、独立预算化上下文注入、跨进程可复用的哈希摘要与依赖图缓存，并新增固定 fixtures 的词法 vs 依赖图 Recall@5/MRR 报告。当前报告包含 11 个任务，其中加入了 Python 隐藏核心模块和 JavaScript/TypeScript 跨语言区分度用例：无 RAG 的首次相关文件命中率为 90.9%，仅词法为 81.8%，加入依赖图后为 100%；依赖图变更现在会增量重算受影响源文件和导入方，未受影响边保持不变；新增 `evals.rag_comparison` 可在同一任务集执行 Repo Map/no-RAG A/B 对照，并单独输出跨文件任务完成率及“需要真实模型证据”的状态；真实跨文件收益证据仍待补充。

### 3.5 可演示的产品闭环

- CLI 和本地 Web UI 使用同一个 Agent Core。
- Web UI 展示模型流、计划、工具调用、审批、Diff 和检查点。
- 文件树、代码编辑器、对话执行区以及会话列表支持拖拽调节，尺寸保存在浏览器本地；平板和手机断点会自动收敛为适合当前屏幕的布局。
- Windows 桌面入口启用原生文字选择与剪贴板桥接，子目录展开不依赖 WebView 兼容性不稳定的选择器；端口冲突时会自动改用独立的本地回环端口，避免误连旧进程。
- 提供可选 PyWebView 桌面入口和 PyInstaller onedir 规格。

## 4. 当前主要缺点

很多能力目前属于“基础版完成”，尚未达到工业级可靠性。以下是风险清单，不代表所有项目都应在同一阶段完成。

### 4.1 运行与恢复

- 可靠取消与单轮 RunBudget V1 已完成：模型请求、审批等待和工具任务共享取消信号，shell 可终止完整子进程树；取消模型流时使用有界清理和 Web 强制取消看门狗，底层传输暂时不响应取消也不会永久卡住 Turn。审批或中断工具跨进程恢复时会沿用已消耗 Token/耗时，不会通过重置预算绕过上限。Web 在停止后主动校准 Session 状态，且允许立即新建或切换其他对话，避免单个异常 Turn 锁死整个界面。
- 时间、Step 和供应商回报 Token 预算已有事件与 UI 遥测；除单 Turn 上限外，可通过 `CODE_HELPER_SESSION_TOKEN_BUDGET` 增加跨独立 Turn 的累计 Token 门禁，并可用 `CODE_HELPER_MAX_OUTPUT_TOKENS` 限制单次生成。DeepSeek / OpenAI-compatible 请求会将配置上限与 Turn、Session 剩余额度取最小值后下传 `max_tokens`；由于输入 Token 仍在响应结束后由供应商报告，总预算依然包含请求后校验边界。
- 取消请求到 `run_cancelled` 的墙钟延迟会从事件时间戳计算并在 Web“智能”面板展示，未完成取消不会伪造样本。
- Windows 本地和 Ubuntu CI 已通过同一子进程树取消测试，形成双平台证据。
- SessionReducer V1 已统一在线/离线归约，能够恢复待审批 Tool Call、最近 Action、修改序列和验证序列；四个关键断点已有恢复矩阵测试。
- 未完成工具会标记 `INTERRUPTED_UNKNOWN` 且不会自动重放；Web 已提供逐调用人工重试/放弃 UI。EventStore 会为缺少序号、事件 ID 或可安全推导 envelope 字段的旧 JSONL 记录做确定性的内存迁移，并在重启后继续序号和因果链；缺失/非法事件类型、跨 Session 混入和非对象 payload 会显式拒绝，不会进入 reducer。任意历史私有格式仍不承诺自动迁移。

### 4.2 验证与权限

- 结构化验证证据 V1 已完成，未知命令、信息命令和失败掩盖命令不能冒充有效验证。
- 工作区可在 `.code-helper/verification.json` 声明全局或按 `project` / `algorithm` 任务类型、相对文件 glob 选择的自定义验证命令；作用域基于 reducer 中真实的读取/修改路径，命令只提升验证证据的可识别性，不绕过工具权限，并会在智能面板显示规则、当前选中命令和配置诊断。
- 相关测试范围在目标命令包含测试路径时会结合 Repo Map 的传递依赖判断覆盖关系；没有图证据时仍采用保守启发式，覆盖率数据和动态调用关系尚未接入。
- 权限能力与审批策略 V1 已分离，能力集合、工作区外路径拒绝和范围化会话授权已落地；Web 审批支持“本会话允许”、智能面板查看和撤销范围授权，以及会话级请求批准、自动批准和完全放开三档策略。默认策略仍保守，完全放开有明确风险提示且不会突破 Ask/Plan 的工具集合。
- 危险命令分类已覆盖常见 PowerShell 删除别名；结构化 `argv` 已优先走无 shell 执行，兼容的 shell 字符串解析仍是 best-effort。

### 4.3 检查点、Hooks 和事件

- 冲突安全回滚 V1 已完成：恢复前比较 Agent 产物哈希，冲突时普通恢复零写入并要求二次确认。
- Web 已提供逐文件选择、恢复差异预览和外部修改二次确认的专用恢复对话框。
- HookManager V1 已支持 Pre/Post、OnVerification、OnTaskEnd 四类 Hook；Runtime 默认注册安全的验证失败和任务结束证据提示，并支持工作区内受限的 argv 外部 Hook 配置（matcher、超时、cwd 和结构化 JSON）。
- EventStore 已支持新事件完整性摘要、尾部损坏诊断、统一脱敏、默认 `causation_id` 因果链和跨 Session 事件保留上限；工具完整输出也支持按字节/文件数清理，Span 可通过脱敏的 Chrome Trace JSON 接口导出到 Perfetto；旧无签名事件会兼容补齐 envelope 字段并记录诊断，未知格式仍拒绝静默恢复。
- shell 已支持 stdout/stderr 增量事件和 Web 终端实时显示，并在 Agent Loop 层按时间/大小窗口合并高频输出；长模型请求会发布不含思维内容的等待心跳；模型请求、审批等待、上下文构造以及各类 Hook 均统一记录 Span 耗时，智能面板可按 Hook 聚合；DeepSeek thinking 工具调用的私有推理状态与标准工具消息已完成多轮协议适配，且不会持久化思维文本。

### 4.4 仓库理解

- Repo Map 按文件名、类型、代码顶层符号和轻量导入图中心性评分；Python 使用 AST，JavaScript/TypeScript、Java、C/C++ 与 Go 使用保守正则提取。
- 当前导入图已连接 Python 模块（含静态字符串动态导入）、JavaScript/TypeScript 本地相对路径、重导出和 class 方法、C/C++ 本地 `#include`、Go `go.mod` 模块内包和 receiver 方法，以及基于 `package` 声明的仓库内 Java 类；同时对能唯一映射到仓库符号的静态函数调用和类方法调用建立保守边，并将调用名写入 Repo Map 证据。Repo Map 还会从 `package.json`、`pyproject.toml` 和 CMake 的显式配置识别构建入口并提升其上下文优先级；更完整的多态调用图、构建工具源码根解析和运行时动态导入仍待补齐。
- `AGENTS.md` 已按目标路径构造作用域规则链，支持 `AGENTS.override.md`、字符预算、自然语言多目标路径解析和 `context_built` 事件；同一目标链中同名标题的不同内容会生成潜在冲突证据，并在轨迹和智能面板展示来源与作用域。
- Step 级历史摘要已改为基于 reducer 事实的结构化模板，记录版本、覆盖消息和事件序列；供应商 tokenizer 和更高保真的语义压缩仍待通过 Eval 后再引入。

### 4.5 缺少 Agent Eval

现有单元、集成测试和 11 项确定性 Eval 已能回答执行契约是否回归；报告现在按 `project`/`algorithm` Profile 分组展示完成率、验证率和 Recall@5；真实模型智能水平和代码 RAG 收益仍需后续评测：

- Agent 在 10 个真实任务中能独立完成几个。
- RAG 是否提高了正确文件首次命中率。
- 新提示词是否降低了任务成功率。
- 算法模式是否真的提高了隐藏测试通过率。
- 安全策略是否拦截了全部预设危险场景。

没有 Eval，后续优化容易停留在主观评价。

## 5. 代码 RAG 是否值得实现

结论：值得，尤其适合“项目编程”模式，但不能实现成普通文档问答式 RAG。

### 5.1 目标

代码 RAG 应解决以下问题：

- 用户描述功能或 Bug 后，Agent 能优先定位实现文件、相关符号和测试。
- 在不把整个仓库塞入上下文的情况下理解跨文件依赖。
- 文件改变后索引能够增量更新，不召回过期代码。
- 召回结果可以解释为什么相关，并能追溯到文件、符号和哈希。

### 5.2 推荐架构

```text
RepositoryIndexer
  -> 文件过滤和哈希
  -> AST/符号级代码切分
  -> 路径、语言、符号、导入和测试关系元数据
  -> SQLite FTS5 词法索引
  -> 可选 Embedding 向量

RetrievalQueryBuilder
  -> 用户任务
  -> 当前计划
  -> 最近工具和错误
  -> 已修改文件

HybridRetriever
  -> 词法召回
  -> Embedding 召回
  -> 导入图和测试关联加权
  -> 新近度与文件哈希校验
  -> 重排序

ContextPacker
  -> 去重
  -> 按 Token/字符预算选择
  -> 注入文件、符号、行号、哈希和相关原因
```

### 5.3 存储建议

优先使用本地 SQLite，而不是外部向量数据库：

- FTS5 保存词法索引。
- 普通表保存文件、符号、导入关系、测试关系和哈希。
- Embedding 作为可选字段或独立本地文件保存。
- Embedding 未配置或失败时退化为词法与依赖图检索。
- 文件哈希变化时只更新对应文件及相关图边。

需要在启动时检测当前 Python/打包环境是否支持 FTS5；不可用时退化为内存词法检索或现有 Repo Map，而不是让 Agent 无法启动。Embedding 通过独立接口注入，不假设 DeepSeek 当前模型端点一定提供向量服务，也不能成为默认演示的硬依赖。

这样更符合当前项目轻量、本地、自研和可降级的设计。

### 5.4 代码切分原则

- Python 优先按 class、function、method 和模块级常量切分。
- 每个 chunk 保留父级 class、完整签名、docstring 摘要和文件路径。
- 超大函数再按逻辑块或行数二次切分。
- 配置、README 和测试文件采用不同切分策略。
- 不应只按固定字符数切割代码，否则容易丢失符号边界。

### 5.5 排序建议

可以使用可解释的轻量评分：

```text
score = lexical_score
      + semantic_score
      + symbol_exact_match
      + import_graph_score
      + related_test_score
      + recently_touched_score
      + repository_evidence_score
```

每个召回结果都应记录各分项，而不是只返回一个不可解释的总分。

### 5.6 RAG 验收指标

- `Recall@K`：正确文件或符号是否出现在前 K 条。
- `MRR`：第一个正确结果的平均倒数排名。
- First relevant file rate：Agent 第一次读取是否命中相关文件。
- 平均文件读取次数是否下降。
- 平均上下文长度是否下降。
- 跨文件 Eval 任务完成率是否提高。
- 文件改变后旧 chunk 不再被召回。

Eval 中每个检索任务必须预先标注正确文件和关键符号，且固定仓库版本。没有 gold label 的主观“看起来相关”结果不能用于计算 Recall@K 或 MRR。至少记录无 RAG、仅词法、词法加依赖图三组结果；Embedding 只有在相同任务集上继续提高指标时才进入默认路径。

只有指标有稳定提升，才能把 RAG 作为可靠的面试亮点。

## 6. 算法编程与项目编程模式

结论：可行，并且比单独增加一个 RAG 开关更有产品辨识度。两个模式必须共享同一个 Agent Loop、工具管线、事件系统和权限策略，不能复制两套核心实现。

建议抽象为：

```text
TaskProfile
  - name
  - prompt_addendum
  - allowed_tools
  - retrieval_strategy
  - planning_policy
  - verification_policy
  - run_budget
```

`allowed_tools` 只能进一步收窄工具集合，最终可用能力必须取 `Profile ∩ Ask/Plan/Act ∩ PermissionPolicy`，Profile 不能扩大权限或绕过审批。Profile 分类结果需要进入事件日志，保证 CLI、Web 和恢复后的 Session 对同一任务使用相同策略。

### 6.1 算法编程模式

算法模式的核心是问题建模和强验证，而不是代码 RAG。

推荐流程：

```text
读取题目
  -> 提取输入、输出、数据范围和边界条件
  -> 选择算法并说明复杂度
  -> 编写实现
  -> 编译或解释运行
  -> 执行样例
  -> 生成边界和随机用例
  -> 必要时与朴素算法对拍
  -> 修复
  -> 输出复杂度和验证证据
```

建议能力：

- 题目约束结构化解析。
- 时间复杂度和空间复杂度预算。
- C++、Python 或 Java 的编译/运行模板。
- 样例、边界、随机和压力测试。
- 对小规模输入使用朴素解法进行 differential testing。
- 区分编译错误、运行错误、超时、输出格式错误和答案错误。
- 命令超时、输出长度和内存使用限制。

随机测试必须使用可记录的 seed；对拍失败要保存最小失败输入，保证缺陷可复现。本项目不是完整沙箱，首版只承诺子进程超时、输出限额和可终止性；无法跨平台可靠限制内存时应明确标为 best effort，不能在演示或文档中声称具备容器级隔离。

最适合面试演示的故事是：

> Agent 写出第一版算法，样例通过，但随机对拍发现边界错误；Agent 根据失败输入定位并修复，最终所有测试通过。

算法模式验收指标：

- 题目约束提取准确率。
- 样例通过率。
- 自建隐藏测试通过率。
- 随机对拍发现缺陷的比例。
- 超时和错误分类准确率。
- 修复后回归验证率。

### 6.2 项目编程模式

项目模式的核心是仓库理解、影响分析、最小修改和相关验证。

推荐流程：

```text
读取项目规则
  -> 代码 RAG 召回文件和符号
  -> 构建影响面和测试关联
  -> 制定计划
  -> 最小范围修改
  -> 运行相关测试
  -> 必要时扩大验证范围
  -> 输出 Diff、兼容性和证据
```

建议能力：

- 使用路径相关的 `AGENTS.md` 规则链。
- 混合检索实现、调用方和相关测试。
- 标记公共 API、配置、数据库结构和依赖变化风险。
- 根据修改文件选择局部测试。
- 验证通过后再考虑完整测试套件。
- 最终报告说明影响范围、未验证部分和遗留风险。

项目模式验收指标：

- 正确文件 `Recall@K` 和首次读取命中率。
- 跨文件任务完成率。
- 无关文件修改数。
- 局部测试选择准确率。
- 平均 Step、Token 和任务耗时。
- 修改后有效验证率。

### 6.3 UI 表达

可以在 Ask / Plan / Act 之外增加任务类型选择：

```text
任务类型：[自动] [算法编程] [项目编程]
```

任务类型决定工作流和验证策略；Ask / Plan / Act 仍然决定权限边界。两者不能混为一套开关。

`自动` 模式只做轻量分类：检测题目是否包含明确输入输出、数据范围和算法要求。分类结果需要展示，用户可随时切换，不能让模型隐式改变安全策略。

实施顺序上先引入 `TaskProfile` 接口和现有 `project` 默认 Profile，确认它不改变当前行为；随后再实现 `algorithm`。当前已完成 Profile 基础接口、保守分类、固定种子 Judge V1、15-case 算法 Eval（含样例、边界、随机、错误检测与失败最小化）、按 Profile 分组的基线报告和同任务 `project`/`algorithm` 确定性对照；仍需用真实模型任务证明相对默认行为的收益后再扩大策略。

## 7. 编辑器方向应该如何优化

不建议近期建设完整 IDE 或大型 LSP 平台。更适合当前项目的编辑器增强包括：

- 展示 RAG 召回的文件、符号、相关原因和分数。
- 从召回结果跳转到对应文件和行号。
- 展示受影响调用方和相关测试。
- Patch 前显示精确锚点和预计 Diff。
- Patch 后检查语法、符号是否仍存在和导入是否有效。
- 将诊断、测试失败位置和 Diff 关联到编辑区。
- 提供“将当前文件加入上下文”和“从上下文移除”的明确控制。

如果后续接入 LSP，应把它当作符号和诊断数据源，不允许 LSP 直接绕过 ToolExecutor 修改文件。

## 8. 推荐实施顺序

每个阶段都是门禁。上一阶段没有形成测试、事件证据和可重复演示时，不进入下一阶段。

`docs/optimization-roadmap.md` 中的 P0 表示这些问题最终都必须认真处理，并不表示应该并行开发。当前执行顺序建议为：

| 执行批次 | 内容 | 原因 |
| --- | --- | --- |
| A | R1 可靠取消与 RunBudget（V1 已完成） | 模型请求中断、双平台子进程树停止、预算事件与 UI 已形成闭环 |
| B | R3 验证证据、R5 冲突安全回滚（V1 已完成） | 伪验证拒绝、证据恢复、原子冲突预检与二次确认已形成闭环 |
| C | R6 最小 Eval 基线（V1 已完成） | 10 项契约、统一评分、双格式报告和 CI 门禁已形成闭环 |
| D | R2 SessionReducer（V1 已完成）、R7 日志脱敏（V1 已完成）、R4 权限分层（V1 已完成） | 先固定恢复语义和审计边界，再补齐端到端证据与边界策略 |
| E | R8～R12、代码 RAG、TaskProfile | R8～R12 V1 已完成；其余能力根据 Eval 瓶颈选择 |

### 阶段 1：先加固现有核心

建议拆成三个独立纵向迭代，而不是一次重写：

1. **取消与预算**：真正取消模型请求和子进程树，并加入 deadline/Token/Step 预算事件。
2. **完成证据**：防止普通成功命令冒充验证，回滚前检测用户外部修改。
3. **恢复与权限**：先用 reducer parity 测试固定现有事件语义，再恢复待审批、修改/验证序列，最后分离能力边界与审批时机。

Token 预算需要区分“硬限制”和“观测限制”：若供应商只在请求结束后返回 usage，本轮只能限制下一 Step 并通过模型 `max_tokens` 控制单次输出，不能宣称能在任意 Token 点精确中断。

详细设计见 `docs/optimization-roadmap.md` 的 R1～R5。

### 阶段 2：建立 Eval

**实施状态：V1 已完成（2026-08-29）**

创建 8～10 个可重复任务：

- 项目问答。
- 单文件缺陷。
- 跨文件功能。
- 外部并发修改。
- 审批拒绝和替代方案。
- 检查点恢复。
- 卡死终止。
- 长输出和取消。
- Session 中断恢复。
- 敏感信息脱敏。

记录完成率、安全拦截率、验证率、Step、Token 和耗时。

Eval 分两层：CI 默认运行 `ScriptedModel` 的确定性契约测试；真实 DeepSeek Eval 必须显式启用，记录模型、推理档位、Prompt 版本、代码提交、运行时间和费用估算。真实模型结果允许波动，不能作为唯一 CI 阻塞条件。

当前 11 项确定性基线的契约通过率、可完成任务完成率、安全拦截率和修改后验证率均为 100%；Repo Map 检索报告另有 10 个带 gold file 的任务，无 RAG/词法/依赖图 Recall@5 分别为 100.0%/90.0%/100.0%，首次相关文件命中率分别为 90.0%/90.0%/100.0%。平均 3.64 Steps、2.6 次工具调用，脚本化 Token 共 1,120。报告保存在 `evals/reports/`，CI 会比较核心比率并上传当次产物。该结果只证明执行契约稳定和受控检索行为，不应表述为真实 DeepSeek 任务成功率。

### 阶段 3：实现代码 RAG V1

最小版本只做：

1. Python AST 符号切分。
2. SQLite FTS5 词法检索。
3. 文件哈希增量更新。
4. 导入关系加权。
5. 召回结果证据和上下文预算。
6. 相关文件 Recall@K Eval。

完成 V1 数据基线后，再增加可选 Embedding 和重排序。不要一开始引入复杂向量基础设施。

进入条件已满足（现有 10 个带 gold file 的确定性任务）；当前报告显示无 RAG/词法/依赖图 Recall@5 为 100.0%/90.0%/100.0%，MRR 为 0.950/0.900/1.000，首次相关文件命中率为 90.0%/90.0%/100.0%，差异来自固定的隐藏核心模块用例。该结果是可复现的受控证据，不等同于真实项目收益；只有在更多真实跨文件任务上获得稳定提升，才继续扩大默认检索策略。

### 阶段 4：实现 TaskProfile

**实施状态：TaskProfile V1 已完成（2026-08-29）**

已实现 `algorithm`、`project` 和保守的 `auto` 分类配置，不修改 Agent Loop 主结构；分类结果通过 `task_profile_selected` 事件记录，工具集合遵循 Profile 与 Ask/Plan/Act 的交集。

- `project`：先作为当前行为的显式默认配置，再接入代码 RAG、影响分析、相关测试选择和项目规则链。
- `algorithm`：已完成基础策略，禁用 Repo Map 注入并收窄工具集合；新增题目结构解析、只读 `analyze_complexity` 复杂度估计、固定种子 `judge_algorithm` 工具和失败输入最小化。复杂度工具对 Python 使用 AST，对 C/C++、Java、Go、JS/TS 使用保守启发式，并明确标注估计边界；自动修复仍待真实工作流 Eval 后再扩展。
- `auto`：只负责选择 Profile，不改变权限模式。

进入条件已满足；算法 Eval 已提供样例、边界、随机和失败输入复现证据，但完整退出条件仍未满足：需要 Profile 对默认行为的收益/安全对比，以及一次端到端“发现并修复缺陷”的演示。

准备两个稳定演示（可用 `python -m evals.interview_demos` 重复运行）：

## 10. 面试表达建议

推荐的一句话介绍：

> 我没有封装现成 Coding Agent，而是从零实现了一个事件驱动、可审批、可恢复、会验证的本地 Coding Agent；随后用代码级混合检索提高大型仓库理解能力，并针对算法题和真实项目采用不同的规划与验证策略。

建议重点讲三个技术故事：

1. **为什么模型说“完成”不等于完成**：通过修改序列和验证序列建立确定性完成契约。
2. **为什么 Agent 修改代码不会轻易覆盖用户工作**：读取哈希、检查点、Diff 和恢复冲突检测。
3. **为什么代码 RAG 不是普通向量搜索**：符号切分、词法与语义混排、依赖图、增量索引和可量化 Recall@K。

不要只说“支持 RAG、支持记忆、支持多模式”。面试官更关心：

- 为什么这样设计。
- 失败边界是什么。
- 如何降级。
- 如何证明比改动前更好。
- 哪些逻辑是自己实现的。

## 13. 每轮迭代的统一交付模板

后续开发对话应以同一模板收尾，防止只增加代码而没有证据：

1. **问题与不变量**：本轮要防止什么失败，哪些行为不能改变。
2. **失败测试/基线**：改动前如何稳定复现，当前指标是多少。
3. **最小实现**：仅修改形成纵向闭环所需的模块。
4. **验证证据**：局部测试、全量测试、必要的浏览器或平台测试。
5. **指标对比**：成功率、延迟、Recall@K、Step、Token 或安全拦截率中至少一项。
6. **已知限制**：平台差异、降级路径和未覆盖风险。
7. **标准提交**：一个逻辑功能一个 Conventional Commit；只有验证通过后推送。
